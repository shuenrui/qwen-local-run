# Qwen Local-Run Directory — UX & product review

**Reviewed:** https://local.host.impossibuild.ai/ (live) + `directory/build.py` @ `8106f10`
**Date:** 2026-09-07
**Reviewer brief:** newcomer to local hosting could not use the page to learn anything.

---

## Verdict in one line

**The data model is excellent and the presentation inverts it.** The beginner
content is collapsed, the expert content is expanded, and the single number the
eye lands on first is the one number the project's own rules say must never be
compared. Nothing below asks you to change the schema or the provenance
discipline — those are the asset. Everything below is presentation.

Three things are true at once and they explain the whole complaint:

1. The page opens with **vocabulary**, not a question the reader can answer.
2. The **filters require the knowledge the reader came to get**.
3. The **card visually shouts a number that is not the number they will feel.**

---

# P0 — Actively misleading. Fix before anything cosmetic.

These are not taste. Each one causes a reader to believe something false.

## P0-1. The headline speed is aggregate throughput on 6 cards, overstating felt speed by up to 17×

`bestSpeed()` in `build.py:348-358` picks the first metric present in this
preference order:

```js
var pref=['decode_code','decode_agg','decode_chat','decode_essay','decode_per_stream'];
```

`decode_agg` sits **second**, above every single-stream metric. So whenever a
setup has an aggregate number, it wins the big bold slot — even when a
single-stream number exists in the same record.

Measured across the dataset, 6 cards do this:

| Setup | Headline shown | Honest single-stream | Overstatement |
|---|---:|---:|---:|
| `qwen38-flash-next-orcarouter-gguf-uncensored` | **489** | 28.7 | **17.0×** |
| `qwen38-27b-r0b0tlab-nvfp4-mtp-sm121-sglang` | **276.4** | 28.4 | 9.7× |
| `qwen38-flash-next-blazux-vllm-hybrid-spark` | **266.8** | 32.5 | 8.2× |
| `qwen35-35b-a3b-bf16-mxfp4-marlin-vllm-spark` | **339.5** | 69.5 | 4.9× |
| `qwen38-27b-nvfp4-bf16head-sglang-dflash2` | **227.6** | 56.6 | 4.0× |
| `qwen38-flash-next-mia-vllm-spark` | **86** | 37 | 2.3× |

Worst case in detail — `qwen38-flash-next-blazux-vllm-hybrid-spark` carries all
of these in one record:

```
decode_per_stream    31      forum
decode_chat          31      forum   single-stream greedy decode on real answers
decode_chat          32.5    forum   kernel-level decode, DET_TOPK=1
decode_agg          266.8    forum   48 concurrent streams, RadixArk NVFP4, 8k ctx
decode_per_stream     5.6    forum   per-stream at 48 concurrent
```

A person sitting alone at this machine experiences **31 tok/s**. The card says
**266.8**. And at the concurrency that produces 266.8, each stream is actually
**5.6 tok/s** — the data even records the collapse, and the UI shows neither.

This directly violates AGENTS.md law #4 and the README line *"Speed sorting is a
discovery aid, not a cross-harness leaderboard."* The design contradicts the
project's stated values.

**Fix:**

- Reorder the preference to put single-stream first:
  `['decode_chat','decode_code','decode_essay','decode_per_stream','decode_agg']`
- **Never show a bare number.** Always render the metric label and the condition
  next to it, at readable size — not as a `.hint` afterthought.
- When a setup has both a single-stream and an aggregate number, show the
  single-stream one as the headline and the aggregate as a secondary line that
  states its concurrency.

Before / after for that card:

```
BEFORE                          AFTER
        266.8  ▸                31 tok/s  ▸
   tok/s agg  forum             one conversation · community-reported
                                ≈ 6× reading speed
                                ├ 266.8 tok/s total across 48 streams
                                └ but only 5.6 tok/s each at that load
```

That "but only 5.6 each" line is the most honest and most educational sentence
the page could possibly contain, and the data for it is already sitting in the
JSON.

## P0-2. The fit badge judges against the smallest listed hardware, so it lies on 13 setups

`hwFit()` at `build.py:363-371`:

```js
ids.forEach(function(id){ var h=HW[id];
  if(h&&h.memory_gb!=null){ if(worst==null||h.memory_gb<worst) worst=h.memory_gb; } });
```

It takes the **minimum** memory across every hardware class the setup lists.
13 setups list two classes with different memory. The clearest failure:

```
qwen38-flash-next-unsloth-gguf-iq1s
  requirements.memory_gb : 72
  hardware               : ["gpu-24gb", "mac-128gb"]
  badge rendered         : "over budget 72GB / 24GB"   ← red
```

A reader on a 128 GB Mac — a machine this setup is explicitly listed for — sees
a red warning telling them it will not fit. It fits with 56 GB to spare.

The inverse is worse for trust: the ten `→ 'fits'` rows are only "fits" against a
24 GB card, and the badge never says *whose* 24 GB it means.

**Fix:** fit is meaningless without a reader. Compute it against the reader's
declared memory (see P1-1). Until a machine is chosen, do not render a
green/red verdict at all — render the neutral requirement: `needs 72 GB
resident`.

## P0-3. 22 of 65 setups render English prose inside a `<code>` block that looks copy-pasteable

`build.py:476` wraps every `run.steps` entry in `<code>`:

```js
var steps = (r.steps||[]).map(function(x){return '<li><code>'+esc(x)+'</code></li>';}).join('');
```

But `steps` is frequently prose, not commands. `qwen38-27b-unsloth-gguf-llamacpp`:

```json
"run": {
  "command": null,
  "steps": [
    "Download unsloth/Qwen3.8-27B-GGUF",
    "llama.cpp with CUDA or Metal, Q4_K_M or smaller to stay on-card"
  ]
}
```

Rendered in monospace under a heading that says **HOW TO RUN IT**, step 2 reads
as a shell command to a beginner. It is a sentence. Pasting it does nothing.

**Fix:** two different visual treatments, chosen per-entry.

- If the string parses as a command (starts with a known binary / contains `--`
  / contains `/`), render monospace **with a copy button**.
- Otherwise render as plain prose in the body font, no `<code>`, no copy
  affordance.
- Add a schema field rather than guessing — `steps: [{kind: "cmd"|"do", text}]`
  is the honest fix. Backfill the 22 offenders.

## P0-4. Half the directory is a dead end and never says so

```
65 setups
33  have no tok/s number at all
33  have no copyable command at all
```

A beginner filters, opens a promising card, and finds `— no speed data` and two
lines of prose. There is no signal *before* the click that this is a lead, not a
recipe.

**Fix:** state the entry's completeness on the collapsed card. A small honest
label costs nothing and sets expectation:

```
✓ Recipe + measured    (has command AND tok/s)
◔ Recipe, unmeasured   (command, no numbers)
○ Lead only            (sourced lane, no command, no numbers)
```

Add it as a filter value too — "show me only setups I can actually run today"
is the single most useful filter for the target reader and it does not exist.

## P0-5. The deployed site is one build stale and is shipping a broken entity

Live HTML renders a literal `&rarr;` in the CONTEXT chip:

```
CONTEXT   262K &rarr; 1M
```

Cause: `sp()` at `build.py:534` passes the value through `esc()`, which escapes
`&` → `&amp;`. Your local source at `build.py:539` already uses the literal
`→` and is correct — the fix just was never published.

```
live  246,835 bytes   grep -c rarr → 1
local 246,843 bytes   grep -c rarr → 0
```

`verify_browser.py:372` already has the guard for this exact class of bug. It
has not been run against the deployed copy.

**Fix:** rebuild + republish. **Standing rule for the agent:** never pass a
pre-escaped HTML entity into `esc()`. Use literal Unicode (`→`, `—`)
in any string that goes through `esc()`. Entities are only legal in the raw
HTML template.

# P1 — Structure. This is the actual redesign.

## P1-1. Lead with the one question the reader can answer

Current first screen, in order: a definition of "runnable setup" → six vanity
stats (`65 setups · 22 models · 29 publishers`) → an epistemology lesson on
evidence tiers → **a collapsed `<details>` containing the best writing on the
page** → six filter dropdowns → 65 results in generation order.

The reader arrives with exactly one question: *"I have this machine — what can
I run?"* The page never asks it.

**Replace the header with a machine picker.** Plain language, no insider ids.

```
┌────────────────────────────────────────────────────────┐
│  Run Qwen on your own machine.                         │
│  Tell us what you have and we'll show what fits.       │
│                                                        │
│  ○ Apple Silicon Mac      ○ NVIDIA GPU (one card)      │
│    M1–M4 Pro/Max/Ultra      RTX 3090 / 4090 class      │
│                                                        │
│  ○ Multi-GPU desktop      ○ DGX Spark / ThinkStation   │
│    Two or more cards        GB10, 128 GB unified       │
│                                                        │
│  Memory:  [  32  ] GB          [ Just show everything ]│
└────────────────────────────────────────────────────────┘
```

Mapping to existing hardware ids — no schema change needed:

| Picker option | `hardware` ids | Memory options | Default |
|---|---|---|---|
| Apple Silicon Mac | `mac-64gb`, `mac-128gb` | 16/24/32/48/64/96/128 | 32 |
| NVIDIA GPU (one card) | `gpu-24gb` | 8/12/16/24/32 | 24 |
| Multi-GPU desktop | `gpu-multigpu-72gb`, `gpu-24gb` | 48/72/96/128 | 72 |
| DGX Spark / PGX | `dgx-spark`, `thinkstation-pgx` | 128 | 128 |

Persist to `localStorage` in a `try/catch`. This selection then drives the fit
verdict (P0-2), the default filter, and the recommendation (P1-2).

## P1-2. Give an answer, not a filtered list

65 of 65 shown, sorted by generation, is a database dump. A directory with no
opinion forces the reader to have one first.

Once a machine is picked, render **one** recommended setup above the list.

```
START HERE ──────────────────────────────────────────────
Qwen3.0-30B-A3B on Ollama
✓ Fits — 19 GB of your 32 GB, 13 GB to spare
Easiest install · one command · no fork needed
~28 tok/s chatting  (community-reported)  ≈ 6× reading speed

  ollama run qwen3.0:30b-a3b                      [copy]

  ▸ Why this one?   ▸ 11 other setups fit your machine
──────────────────────────────────────────────────────────
```

Selection algorithm — deterministic, no ML, ~30 lines:

```
1. Disqualify: requirements.memory_gb > user_mem
2. Disqualify: engine.requires_fork === true
3. Rank by install ease (lower wins):
     ollama 1 · lm-studio 1 · llama-cpp 2 · mlx-lm 2 · vllm 3 · sglang 3 · custom-fork 4
4. Tie-break: has a copyable command
5. Tie-break: provenance tier  box > forum > vendor > none
6. Tie-break: highest single-stream tok/s
7. Tie-break: most headroom (user_mem - memory_gb)
```

Emit the reason string from whichever rules decided it, so "Why this one?"
is generated, not written. This is also self-documenting when the data changes.

## P1-3. The filters demand the knowledge the reader came for

`Quant: any` and `Engine: any` are unanswerable if you do not yet know GGUF
from NVFP4, or Ollama from vLLM. Six equal-weight dropdowns present the reader's
*only* answerable question (hardware) as the third of six.

**Fix:** two tiers.

- **Always visible:** search + the machine picker's outputs + a single
  `Sort:` control.
- **Behind "More filters":** engine, quant, evidence tier, memory budget.
  Label each with a one-line plain-English hint on the option group, e.g.
  `Engine — the program that runs the model`.

**Hard constraint:** `verify_browser.py` drives `#q`, `#f-engine`, `#f-hw`,
`#f-quant`, `#f-tier`, `#f-fit`, `#sort`, `#expand-all`, `#reset` at 1440×1000
via `select_option` / `fill`, which require visibility. So the advanced panel
must be **visible by default at ≥641px** and collapsed only under the mobile
media query. Do not put those controls inside a closed `<details>` — the gate
will fail. At 390px the suite only touches `#q`, so a mobile-collapsed panel is
safe.

## P1-4. The card is chip soup with no hierarchy

Current head renders up to 9 chips at identical visual weight
(`build.py:459-468`), mixing five unrelated categories:

```
SGLang | MIXED | NVIDIA DGX Spark | by azampatti | tools | thinking | fits 110GB/128GB
 engine   quant     hardware          author       capability        the verdict
```

The one chip that decides everything for a beginner — *does it fit* — is last
and looks like `thinking`.

**Fix — three explicit levels:**

```
LEVEL 1  the verdict          ✓ Fits — 19 GB of your 32 GB      (large, coloured)
LEVEL 2  what it is           Qwen3.0-30B-A3B on Ollama         (title)
         plain-English        "MoE that wakes 3B per token, so it
                               runs fast on a slow-memory box."  ← slug_note, MOVE UP
LEVEL 3  everything else      Ollama · GGUF Q4 · 24 GB GPU · by unsloth   (one muted line)
         warnings only loud   ⚠ needs fork
```

`slug_note` is present on **all 65 setups** and is currently buried inside the
collapsed body at `build.py:515`. It is the plain-English sentence the reader
needs and it is hidden. Move it into the collapsed card head. This is the
single highest-value, lowest-effort change in this document.

Demote `vision` / `tools` / `thinking` to a text line — `Can: images, tools,
thinking` — instead of three chips competing with the verdict.

## P1-5. Define terms where they appear, not in a collapsed block at the top

The glossary at `build.py:250-258` is genuinely good writing and it is closed
by default, at the top, before the reader has met any of the terms it defines.

**Fix:** keep a short always-open version, and additionally attach definitions
to first use inline:

```html
<span class="term" data-def="Tokens per second — roughly, how fast text
appears. About 5 tok/s is comfortable reading speed.">tok/s</span>
```

Dotted underline, click to open a small popover. Implement the popover with
`position: fixed` and clamp `left` to the viewport, because
`verify_browser.py` asserts `no horizontal overflow at 390px` and an
absolutely-positioned tooltip near the right edge will break that check.

Terms to wire: `tok/s`, `TTFT`, `quant`, `GGUF`, `NVFP4`, `MoE`, `active
params`, `resident`, `KV cache`, `MTP`, `needs fork`, `box`/`forum`/`vendor`.

## P1-6. Nothing explains what local hosting *is*, or what it costs

The page assumes the reader already wants a specific checkpoint. A newcomer
does not know: that they will download 15–70 GB, that "engine" and "model" are
separate things, or what they get at the end.

**Add a short always-visible section**, above the list, three steps:

```
1. Pick a model   The weights. A big file you download once from HuggingFace.
                  Bigger = smarter and slower. "Quant" = compressed, so it fits.
2. Pick an engine The program that loads those weights and answers you.
                  Ollama is the easiest. vLLM and SGLang are faster and harder.
3. Run it         One command for the easy paths. A chat box on localhost,
                  no account, no API bill, works offline.
```

Written at roughly this length. Not a tutorial — an orientation.

# P2 — Polish

## P2-1. Mobile is 25,183 px tall

Measured at 390×844 on the live site. Six stacked full-width dropdowns occupy
most of the first screen before a single result appears. P1-3 fixes the cause.
Additionally: collapse model groups on mobile by default, showing
`Qwen3.8-27B — 4 setups ▸`.

## P2-2. The six header stats are vanity metrics

`65 setups · 22 models · 6 hardware · 7 engines · 29 publishers · 4 measured on
our box` tells a newcomer nothing and occupies the most valuable space on the
page. Move to the footer. Keep `#counts` and `#gen` element ids so
`renderCounts()` at `build.py:596` does not throw.

## P2-3. Reading-speed anchor

Give every tok/s number a human comparison — this is the most educational
thing you can add for the cost:

```
31 tok/s  ≈ 6× reading speed
 4 tok/s  ≈ slower than you read
```

**Verify the constant before shipping.** ~5 tok/s ≈ comfortable adult reading
speed assumes ~250 wpm and ~0.75 words/token. Confirm the ratio you want and
state it once, in the glossary, so the multiplier is auditable.

# Constraints the implementing agent must not break

1. **`site/index.html` is generated.** Change `build.py` or `data/`. Never hand-edit. (AGENTS.md law #5)
2. **Preserve these ids/classes** — `verify_browser.py` drives them: `#q`,
   `#f-engine`, `#f-hw`, `#f-quant`, `#f-tier`, `#f-fit`, `#sort`,
   `#expand-all`, `#reset`, `.card`, `.copy`, `#counts`, `#gen`, `#hint`, `#out`.
3. **Reset must clear the search box** — the suite asserts it explicitly.
4. **No horizontal overflow at 390px** — asserted. Watch tooltips and tables.
5. **Never pass an HTML entity through `esc()`.** Literal Unicode only. (P0-5)
6. **Do not blend provenance tiers**, do not aggregate quality canaries into a
   score, do not drop negative results. (AGENTS.md laws #1–#4)
7. **Python 3 stdlib only** for `build.py`. No runtime dependencies, no backend,
   must work from `file://`.
8. **Do not publish.** `ifhost publish` replaces the entire live site; that is
   the owner's call, run only on explicit go-ahead.

# Definition of done

```bash
bash directory/tools/install_verify_env.sh   # once
python3 directory/check.sh                   # validate → links → build → browser
```

Must print **0 errors**, all source URLs resolving, and the browser suite green
at both 1440 and 390. Then screenshots for review. **No publish without
explicit go-ahead.**

Acceptance test, in plain English — hand the page to someone who has never run
a model locally and give them one sentence: *"You have a 32 GB Mac."* They
should reach a copyable command in **under 60 seconds** without asking what a
word means. Today that journey requires knowing what a quant is before they can
touch a single control.
